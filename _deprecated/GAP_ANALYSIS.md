# 外部知识注入与方案差异分析

> 分析基于：wiki 方案文档 + 项目代码现状 + Palantir 调研结果
> 2026-07-11

## 一、关键问题：我们需要的不只是 PRD 内联关系

你提出的点非常关键：**Palantir 的关系是跨数据源的确定性映射**——一个 Object Type 的 FK 指向另一个 Object Type 的 PK，这些关系可能跨越 ERP、CRM、IoT 等多个系统。这意味着 Palantir 的 Ontology 天然包含"外部知识"。

而我们的方案目前只考虑了**PRD 文档内部**的关系抽取，缺少以下外部知识源：

### 1.1 缺失的外部知识源

| 外部知识类型 | 在 Palantir 中的对应 | 在我们的方案中的现状 |
|-------------|---------------------|-------------------|
| **公司定位/战略** | 隐含在业务数据中（订单量、客户类型等） | 未考虑 |
| **经营状况** | 通过 ERP 数据映射为 Object | 未考虑 |
| **研发状况** | 通过代码仓库/工单系统映射 | 仅方案中有"代码静态分析"计划，未实现 |
| **组织架构** | 通过 HR 系统映射为 Employee/Team Object | 未考虑 |
| **行业通识/领域知识** | 通过外部数据源（如监管数据）映射 | 未考虑 |
| **技术架构知识** | 通过基础设施数据映射 | 未考虑 |
| **历史 PRD / 已有代码库** | 通过 Pipeline 导入历史数据 | 附录 B 有方案设计（分阶段融合策略），但未实现 |

### 1.2 当前代码实现了什么

```
parser/llm_extractor.py 中的 PRDExtractor.extract()
    ↓
只接受一个输入参数: prd_text (单份 PRD 文本)
    ↓
LLM 从该文本中抽取实体和关系
    ↓
输出: {entities: [...], relations: [...]}
```

**局限：**
- 输入只有一份 PRD 文本，没有其他上下文
- LLM 的"先验知识"只能靠模型自身的训练数据（通用知识）
- 无法感知公司特定的语境（如"这个模块在我们公司是哪个团队负责"）
- 无法感知经营层面的约束（如"Q3 预算削减 30%"→ "优先级调整"）
- 无法感知组织层面的依赖（如"这个需求需要 A 团队配合，但 A 团队在全力做另一个项目"）

## 二、与 Palantir 的完整差异对比

### 2.1 数据源维度

```
Palantir:
    ERP (财务) ─────────┐
    CRM (客户) ─────────┤
    HR 系统 (组织) ─────┤
    IoT (设备) ─────────┤──→ Hydrate 联邦映射 ──→ Ontology
    Git/工单 (研发) ────┤
    外部数据源 ─────────┘
    所有关系是确定的（外键/连接表）

我们的方案（现状）:
    PRD 文档 ──→ LLM 抽取 ──→ Ontology
    关系是概率性的（LLM 推理）
```

### 2.2 关系确定性维度

| 维度 | Palantir | 我们（现状） |
|------|----------|------------|
| 关系来源 | 数据库外键、Join Table 的确定性映射 | LLM 从非结构化文本抽取 |
| 准确性 | 100%（数据源决定） | 依赖 LLM 质量 |
| 跨数据源关系 | 原生支持（Hydrate 联邦查询时关联） | 不支持 |
| 关系语义 | 语义化命名（`employer`, `assigned_aircraft`） | 8 种通用类型（depends_on, implements 等） |
| 关系基数 | 支持 one-to-one, many-to-one, many-to-many | 不支持 |
| 反向关系 | 自动生成反向 Link | 不支持 |

### 2.3 推理能力维度

| 维度 | Palantir | 我们（现状） | 我们（方案计划） |
|------|----------|------------|----------------|
| 推理引擎 | Function（编程式），开发者手写逻辑 | 无 | engine/ 模块（未实现） |
| 遍历方式 | OSDK 遍历 + Spark 分布式计算 | 无 | SQLite 递归 CTE（未实现） |
| 冲突检测 | Function 中手写 | 无 | `detect_conflicts` MCP Tool（未实现） |
| 影响分析 | Function 中手写 | 无 | BFS 影响链遍历（未实现） |
| 派生属性 | Function 实时计算 | 无 | 未计划 |
| LLM 推理 | AIP Logic 可选 | 无 | 未计划 |

### 2.4 存储与查询维度

| 维度 | Palantir | 我们（现状） | 我们（方案计划） |
|------|----------|------------|----------------|
| 存储引擎 | 自研分布式对象数据库 | 无存储 | SQLite（未实现） |
| 关系存储方式 | 索引化邻接表 | 无 | relations 表 + 递归 CTE |
| 查询方式 | SQL / OSDK / Vertex | 无 | MCP Tools |
| 历史版本 | 全历史快照 | 无 | Event Sourcing（未实现） |
| 权限模型 | 行级+列级+Action 级 | 无 | 未计划 |

### 2.5 Action（写回）维度

| 维度 | Palantir | 我们（现状） | 我们（方案计划） |
|------|----------|------------|----------------|
| Action 定义 | Action Type + Function | 无 | 未计划 |
| 前置校验 | 校验规则 | 无 | `detect_conflicts` 的阻止机制（未实现） |
| 写回目标 | 源 ERP/CRM/MES | 无 | 代码注释 / PRD 文档 |
| 审计日志 | 全链路 | 无 | feedback_log 表（未实现） |

## 四、关键发现与建议

### 4.1 核心差距总结

```
Palantir 能做到的           我们能做的（现状）             我们缺少的
────────────────────────────────────────────────────────────
多数据源融合映射         单 PRD 文档抽取              公司级语境 + 行业知识
确定性关系（FK）         概率性关系（LLM）             代码/Issue 关系验证
编程式推理（Function）   无推理能力                   冲突检测 + 影响分析
分布式存储 + 索引       无存储                        SQLite 存储层
OSDK / Vertex 查询       无查询能力                    MCP 查询工具
Action 写回业务系统      无写回机制                    Action 机制
全历史版本快照           无版本管理                    Event Sourcing
```

### 4.2 建议的优先补充事项

**第一批（补齐 Palantir 的核心能力）：**
1. **SQLite 存储层** — entities + relations 表，这是所有后续能力的基础
2. **MCP 正式服务器** — 把 Parser 和 Storage 串起来
3. **公司级语境注入** — 在 LLM 抽取 prompt 中加入公司背景信息（经营状况、组织架构等）

**第二批（建立 Palantir 不具备的差异化能力）：**
4. **自监督反馈机制** — 利用开发结果验证关系准确性
5. **代码静态分析** — 从代码 import 关系验证 PRD 中的依赖关系
6. **冲突检测 + 影响分析** — 基础的推理能力

**第三批（达到 Palantir 的工程水准）：**
7. **实体级版本管理** — Event Sourcing
8. **Action 写回机制** — MCP Tool 写回代码注释/PRD
9. **行业知识注入** — 预置关系模板 + 领域实体类型

### 4.3 关于"外部知识注入"的具体实现思路

你提出的问题——从公司定位、经营状况、研发状况、组织架构、行业通识等获取关系映射——本质上是要解决**LLM 抽取时缺少上下文**的问题。

可行的实现方式：

```
方式 A: 在 LLM 抽取 prompt 中加入公司上下文描述
    prompt = f"""
    公司背景: {公司定位描述}
    组织架构: {团队信息}
    当前阶段: {经营/研发状况}
    
    请从以下 PRD 中抽取实体和关系...
    """
    优点：最简单，立即可做
    缺点：公司知识变了要改 prompt，不适合长期维护

方式 B: 公司知识作为先验 Ontology 加载到 SQLite
    CREATE TABLE company_knowledge (
        entity TEXT,       -- 公司实体名（如 "支付团队"）
        type TEXT,         -- entity_type
        properties JSON,  -- 属性（如 {"负责人": "张三", "当前负荷": "80%"}）
        relations JSON    -- 关系（如 [{"target": "订单模块", "type": "owns"}]）
    );
    在解析 PRD 时，将公司知识作为已有 entity 传入 postprocessor 的
    resolve_with_ontology() 进行消歧关联
    优点：可动态更新，可版本管理

方式 C: 行业通识作为预置 Schema
    如 SaaS 行业预置实体类型：租户、套餐、订阅、计费规则等
    如 金融行业预置：交易、风控规则、监管约束等
    在 llm_config.yaml 中配置行业模板选择
    优点：冷启动质量提升，减少通用关系命名歧义
```

**建议：从方式 A 开始快速验证效果，后续演进到方式 B 实现可持续维护。**
